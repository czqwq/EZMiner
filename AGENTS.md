## What this is

EZMiner is a **Minecraft Forge 1.7.10** chain-mining mod for the **GregTech: New Horizons (GTNH)** modpack. It runs on both client and server, and uses **Mixin** minimally (fortune-uncap, fast-harvest, and the pause-menu "Mod Options" replacement).

## Build & Validate

```bash
./gradlew spotlessApply build
```

- **No tests exist** — validation is a successful build (Spotless `apply` + `check` + Checkstyle + reobf + jar).
- Build uses the GTNH convention plugin with **Jabel** (Java 17 syntax targeting JVM 8) and **Mixins** (`usesMixins = true`, single early config `mixins.EZMiner.json`; the late config and its `ILateMixinPlugin` scaffolding were dead code and have been removed). `MixinGuiIngameMenu` is listed under the config's `client` array because it targets a client-only class.
- The Mixin annotation processor generates `build/tmp/mixins/mixins.EZMiner.refmap.json`; vanilla/FML-targeted mixins use MCP names and rely on it (production remap).
- The three fortune-uncap mixins (`MixinGTOreAdapter`/`MixinBWOreAdapter`/`MixinGTPPOreAdapter`) target `gregtech.common.ores.*`, which only exists on GT5U generations shipping the new ore system. They are a silent no-op on the older 5.09.x line (see `CLAUDE.md` §Mixins).
- Note: `gtnh.settings.blowdryerTag=0.2.2` (Blowdryer) fetches Spotless config from GitHub raw; if the Gradle JVM cannot reach it, build with `-Pgtnh.settings.blowdryerTag=LOCAL` and put the three files (`spotless.gradle`, `spotless.importorder`, `spotless.eclipseformat.xml`) in `gtnhShared/`.

## Architecture overview

- **Legacy layer** (`core/`, `client/`, root package): `Manager` (per-player event wiring), `BaseOperator` (server-tick harvest batching), `core/founder/` (`BasePositionFounder` hierarchy), HUD/render/key input.
- **Chain subsystem** (`chain/`): `state/` (per-player `ChainPlayerState`, `ChainStateService`), `lifecycle/`, `planning/` (`ChainPlanner` scaffold, `ChainPreCalcEngine`/`Cache`), `execution/` (harvest executors, `ChainDropCollector`, `XPDropHandler`, special-mode handlers), `mode/`, `network/`, `watchdog/`.
- **Mixin** (`mixin/early/`): fortune uncap, `MixinItemInWorldManager` fast harvest, `MixinGuiIngameMenu` (pause-menu "Mod Options" replacement; registered in the config's `client` array).
- **Compat** (`compat/`): GT5, TinkersConstruct, Natura, Witchery, Bandit, VisualProspecting, EndlessIDs-aware writes.

## Harvest / world-mutation paths (server thread)

Three paths exist; all mutation runs on the server thread:

1. **Per-block fast path** — `BlockHarvestActionExecutor.execute()` → mixin `ezminer$tryHarvestBlockFast` → `World.setBlock(..., air, 0, 2)` (flag 2 = client update, no neighbor notify).
2. **Batch chunk-cached path** — `ChunkCachedHarvester.harvestNext()` → `ChunkBlockWriteHelper.writeAirToEbs()` (direct `ExtendedBlockStorage.func_150818_a`), then `markBlockForUpdate` + height-map update. **Metadata is always zeroed** there to avoid "air + stale GT meta" blocks (`name.0`).
3. **TE path** — vanilla `tryHarvestBlock` for `block.hasTileEntity(meta)`.

**Neighbor notifications** (`onNeighborBlockChange`) are fired **by default** after each harvest batch, deduplicated, so water/sand/gravel/cactus/tall-grass react (flow / fall / break / pop) instead of floating next to a mined cavity. Controlled by `Config.notifyNeighborsOnChainBreak` (default **on**; cost is surface-proportional, not volume — turn off only for max-FPS). Note: vanilla *grass blocks* above a mined void stay floating even in normal mining (no neighbor reaction exists for them); grass *plants* (`tallgrass`, `BlockBush`) DO pop via `onNeighborBlockChange` and are covered by this fix.

**Tree felling**: `LogFounder` + `ChunkBlockWriteHelper.flagNeighbouringLeavesForDecay()` (called for removed wood blocks) flags adjacent leaves via vanilla `beginLeavesDecay`, so canopies decay like vanilla instead of floating.

**CoFH Core water**: CoFH Core's ASM replaces water with `BlockTickingWater extends BlockDynamicLiquid` (the **flowing** block), whose `onNeighborBlockChange` is a no-op for water. `Blocks.water` (the source) is replaced by `BlockWater extends BlockStaticLiquid`, whose `onNeighborBlockChange` **does** react — so the "no-op" premise holds for the flowing replacement only. `CoFHWaterBridge.ensureWaterFlowUpdate()` (called after every notified non-air neighbour in `notifyBatchNeighborChange`) **deterministically fills the vacated hole below any notified water neighbour** (flowing water level 8, flag 3 — the vanilla `func_149813_h` downward flow) and also schedules the neighbour's flow tick when its **material** is water, so water settles with or without CoFH — **material-keyed** (`neighbour.getMaterial() == Material.water`), not `instanceof BlockDynamicLiquid`, and no CoFH compile dependency. The fill test is vanilla's replaceability predicate (material is neither water nor lava and does not `blocksMovement()`), not an `== Blocks.air` identity check.

**Grass-plant/bush family**: tall grass/flowers/ferns/saplings (`BlockBush` subclasses) should pop when their support is mined. `BushSupportBridge.popIfUnsupported()` re-verifies `canBlockStay` after the notification and drops+clears a still-present unsupported plant, mirroring vanilla `BlockBush.checkAndDropBlock` — immune to mods that co-opt `onNeighborBlockChange`.

**Hodgepodge interaction**: Hodgepodge replaces `ChunkProviderServer`'s `LongHashMap` with an owner(server)-thread `ServerThreadLongHashMap` (background reads use snapshots) and its `MixinWorld_PreventChunkLoading` short-circuits neighbor notifications on unloaded chunks. All EZMiner world writes/notifications are server-thread-only (never background), so no new off-thread warnings are introduced; `Config.suppressHodgepodgeWarnings` filters the pre-existing founder-thread logs.

## Network threading

1.7.10 `SimpleNetworkWrapper` dispatches server handlers on the netty IO thread. `MainThreadEnforcer.guardedNull()` now **actually defers** server-mutating handlers to the next server tick via `MainThreadEnforcer.DEFERRED`, drained by `PlayerManager.onServerTick`. `PlayerManager.managers` is a `ConcurrentHashMap` for the same reason.

## Public API for other mods

`com.czqwq.EZMiner.api.EZMinerAPI` — programmatic chain control:

- Server (must run on server thread): `setChainKeyHeld(UUID, boolean)`, `startChain(UUID, Vector3i)`, `setMainMode/setBlastSubMode/setChainSubMode/setSpecialSubMode(UUID, int)`, `setMode(UUID, main, blast, chain, special)` (‑1 = untouched).
- Queries: `isKeyHeld(UUID)`, `isOperateActive(UUID)`, `isActive(UUID)`, `getChainActivationMode()`.
- Client: `pressChainKeyClient()/releaseChainKeyClient()` (send `PacketKeyState`), `applyModeClient(...)` (send `PacketChainModeSwitch`), `setChainActivationMode(int)`.
- Server-side calls are authoritative writes (equivalent to receiving trusted packets); client calls only send C→S packets, keeping server authority.

## Coding conventions

- Root package `com.czqwq.EZMiner`; run `./gradlew spotlessApply` before committing (Google Java Format).
- New server config field: declare in `Config` (server section), load in `loadServerOnlyInternal`, save in `saveServerConfig`, sync via `PacketServerConfig` + `applyServerRuntimeConfig`, save via `PacketSaveServerConfig`, and add a GUI row (Server tab; when appending at the end bump `SERVER_CONTENT_ROWS` and update `isSectionBreak`/`getRowLabelKey`/`initGui`/`actionPerformed`/`updateScrolledPositions`/`drawServerTab`/`updateTabVisibility`/`applyAndSaveServerConfig` at the new row + `lang`).
- New network packet: register in `NetworkMain`, extend `AbstractPacket` (GTNH lib).
- Do NOT add Mixins for core mining functionality; prefer the EBS/chunk-cached pure-Java helpers which are EndlessIDs-safe (`func_150818_a` / `getBlockByExtId`).

## Recent changes (2026-07)

- **Bug fixes (server-thread, batched, near-zero hot-path cost):** GT-ore `name.0` (metadata zeroing in `writeAirToEbs`), floating water/sand/grass (opt-in `notifyNeighborsOnChainBreak` batched+dedup neighbor notify), tree leaves persist (vanilla `beginLeavesDecay` flag for removed wood).
- **Threading:** `PlayerManager.managers` → `ConcurrentHashMap`; `MainThreadEnforcer` real server-thread deferral; `ChainPreCalcEngine` sub-chunk bounds check.
- **Blast multi-threaded shell scan resumes across ticks:** `BasePositionFounder.run1MultiThreaded` now keeps a per-strip cursor (`StripScan`) and re-runs an incomplete shell instead of advancing `curRadius`, so a tick-end worker pause can no longer drop the unscanned tail of a shell layer (the "striped residue" bug). Chain / planting / tunnel / log founders are unaffected (they never abort a shell mid-scan).
- **Perf pass (hot-path overhead only, no behavior change):** blast shell-scan workers read the tick pause flag directly instead of calling `consumeBudget()` (drops a `Thread.currentThread()` + `isInterrupted()` per position); `ChainPositionFounder.collectNeighbours` now performs the atomic visited admission on the collecting thread, so each neighbour costs one hash op and one `Vector3i` instead of one per adjacent node (workers use `checkCanAddAfterVisited`); `ParallelTick` no longer allocates a stream + temp list on every server tick; `ChainPreCalcEngine.stop` only pushes the client clear packet when a pre-calculation actually reached the client (it previously sent one packet per idle player per tick); client preview: `SpaceCalculator` replaced the per-block `HashSet` + `Vector3i` allocations with a reused `boolean[12]` edge mask and probe, `RenderCache` reuses its direct staging buffers instead of allocating off-heap memory per upload, and `MinerRenderer` rebuilds the mesh only when `SpaceCalculator.hasChange`.
- **Blast "ore only" no longer mines non-ore metadata variants:** `DeterminingIdentical`'s ore cache changed from a per-`Block` boolean to a per-`Block` **metadata bitmask** (`computeOreMetaMask`). Block-class detectors (GT5U old/new/legacy, BartWorks, GT++, AE2, EFR) and the unlocalized-name fallback still mark every metadata, but the OreDictionary `ore*` fallback is now evaluated per metadata. Previously any block with one ore metadata was classified wholly as ore, so e.g. Galacticraft's `blockMoon` (meta 0/1/2 = copper/tin/cheese ore, meta 3/4/5-13/14 = moon dirt / **moon rock** / turf / bricks, all one `Block`) made the blast "ore only" mode chain-mine plain moon stone around a real ore. `OreFounder` also uses the new pre-fetched `isOreBlock(Block, int, Vector3i, EntityPlayer)` overload, dropping two world lookups per candidate.
- **Unbreakable blocks (hardness < 0) are no longer chain-mined by a survival player:** new single-source-of-truth predicate `DeterminingIdentical.isUnbreakable(EntityPlayer, Block, int, int, int)` → `getBlockHardness(player.worldObj, x, y, z) < 0`, with creative deliberately exempt. Vanilla only enforces this **client-side** (`Block.getPlayerRelativeBlockHardness` returns 0 for a negative hardness, so a survival client never accumulates progress and never sends the finishing dig), and all three EZMiner harvest paths write the world server-side — so blast all-blocks / same-type / inverse / tunnel, chain, ore, GT-vein and crop modes happily removed bedrock, end portal frames, end portals, command blocks and any other `hardness = -1` block (only `Blocks.bedrock` was ever hard-coded out). The predicate is consulted (a) in **every** `checkCanAdd*` gate, placed after the cheap identity filters and **before** `skipHarvestCheck` so the client preview matches the server, and (b) as a safety net in `BlockHarvestActionExecutor.execute`/`executeBatch`/`executeWithPreResolved` and `ChunkCachedHarvester.harvestNext`, which also covers positions injected by `NaturaSaguaroCompat.cascadeUnsupportedNeighbors` and blocks whose type changed after admission. Cost: one virtual `getBlockHardness` call per *accepted* candidate (gates) or per *mined* block (executors) — never per scanned position. `Config.stopOnUnbreakable` is a separate feature (tool eligibility) and was left untouched.
- **API:** `EZMinerAPI` (above); `Manager.startChain` is now public.
- **Dead code:** removed `MinerModeState.previousMainMode()`. Reviews in `docs/review/` also flag the `chain/mode` package and `chain/planning` planner scaffolds as write-only (documented, not yet deleted).
- **Perf review** (`docs/review/perf-mixin-review.md`): A1 (pre-fetched block/meta into `DeterminingIdentical.identical`) already implemented in `ChainPositionFounder`; further wins (A3 founder chunk/EBS cache) are documented, not yet applied.

## Recent changes (2026-09 — full audit + fix pass)

Seven parallel audits (core, chain, client, infra, compat, tmp-world, tmp-tools) over `src/main/java` plus the third-party sources under `tmp/`, a verified fix ledger, and three repair/verification rounds. Reports: `docs/review/agent-teams/{core,chain,client,infra,compat}-audit.md`, `tmp-{world,tools}-breakage.md`, `fix-ledger.md`, `fix-report.md`, `verification-report.md`, `review-round{1,2,3}.md`, `final-report.md`. **Behaviour changes worth knowing** (no build or formatter was run in that session — see `final-report.md` §7):

- **Protection gate on every removal branch:** `World.canMineBlock(player, x, y, z)` is now consulted **unconditionally** for every block about to be removed (`BlockHarvestActionExecutor.execute`/`executeBatch`/`executeWithPreResolved`, `ChunkCachedHarvester.harvestNext`, `BlockSwapModeHandler`, `PlantingModeHandler`) and the Forge `BlockEvent.BreakEvent` is fired when `Config.fireBreakEvent` is on **or** a protection mod that cancels through it is loaded (probe in `ChainBreakEventHelper`). Previously an automated chain skipped both, so ServerUtilities-style claims could be mined. Cost: one cheap `canMineBlock` per removed block.
- **Tree-felling radius clamped:** `Config.clampLogBigRadius` bounds `logBigRadius`/`clientLogBigRadius` to `8..64` (default changed from 1024 to 64) and `highRadius` is capped in `LogFounder`, whose shell walk was rewritten to visit only the positions added by each shell. The mode could not finish at the old default.
- **Non-TE `Block.removedByPlayer` overrides are honoured** via the new `compat/RemovedByPlayerBridge` (identity-keyed per-`Block` probe) on both the fast path and the vanilla escape of the two executors; the plain path keeps `setBlock(...,air,0,2)` so the batched neighbour-notify contract is unchanged.
- **Vanilla `Item.onBlockStartBreak` is replayed** on the fast path (and honoured as "block consumed"), **except for Tinkers' Construct tools**, which stay on `TinkersConstructLevelingBridge` so `beforeBlockBreak` fires once and the TiC AOE tools cannot recurse per chained block.
- **Drops and XP are flushed before runtime cleanup** on logout/respawn/dimension change (`ChainLifecycleService.stopRuntime` → `Manager.flushDrops()` when a world exists); world unload stops the operator but keeps the collector instead of discarding it.
- **Nine server fields are now synced** to the client (`enableChainWatchdog`, `enableDropFallbackChain`, `enableMainThreadGuard`, `enableBudgetDeadline`, `enableConfigValidation`, `enableSafeReflection`, `chainWatchdogTimeoutTicks`, `enableToolBreakHandoff`, `toolBreakHandoffTimeoutTicks`) through `PacketServerConfig` + `Config.applyServerRuntimeStability`; the tool-break handoff is decided by the server only (the client no longer re-gates it). `addExhaustion` is validated (`NaN`/±∞ rejected), and the plant clamps agree at `1..12`/`1..256`.
- **Honest config labels where a knob no longer does anything:** `maxFortuneLevel` is marked "NOT ENFORCED — dead setting" and `enableBudgetDeadline` (plus the dead `Pauseable.errorCount`/`deadlineNanos`) is marked inert with a removal entry in `docs/todo.md`. The chain watchdog is now armed on progress instead of on registration and refuses to compare against an unavailable-server sentinel; cached pre-calculation sync is append-only (`PacketCachedBlockSync.startIndex`).
- **Client input:** the chain key is released before a GUI opens (a screen swallows the key-release event), and scroll-wheel sub-mode switching is skipped while any screen is open.
- **Mixin scaffolding:** the dead `Mixins`/`MixinCapabilityPlugin`/`ILateMixinPlugin`/`TargetMod`/late-config set and `Config.enableMixinCapabilityGates` are gone; `MixinGuiIngameMenu` sits in the config's `client` array. The three ore mixins keep `required:false` and no `require` (deliberate: their targets do not exist on GT5U 5.09.x).
