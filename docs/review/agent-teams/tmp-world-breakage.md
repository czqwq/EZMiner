## 2. Ranked confirmed breakage (EZMiner file:line + minimal fix)

**F1 — HIGH — ServerUtilities chunk-claim protection is bypassed by all three harvest paths.**
`su/serverutils/data/ClaimedChunks.java:480-485` registers `@SubscribeEvent(priority = HIGHEST) onBlockBreak(BlockEvent.BreakEvent)` and calls `event.setCanceled(true)` when the actor may not edit the chunk. EZMiner only fires that event when `Config.fireBreakEvent` is on — default **off** — `EZM/chain/execution/ChainBreakEventHelper.java:32-35` (`if (!Config.fireBreakEvent) return null;`), consumed at `EZM/chain/execution/ChunkCachedHarvester.java:142-143`, `EZM/chain/execution/BlockHarvestActionExecutor.java` (same helper) and `EZM/mixin/early/MixinItemInWorldManager.java:49-54,108` (which *accepts* a pre-fired event but writes `setBlock(...,2)` at line 108 regardless). EBS writes bypass `World.setBlock` entirely, so `WorldServer.canMineBlock`/`isBlockProtected` never runs either.
*Minimal fix:* fire `ForgeHooks.onBlockBreakEvent` (or at least call `world.canMineBlock(player,x,y,z)`) **unconditionally** for every removed block in all three paths and abort the block on cancellation; keep `Config.fireBreakEvent` only as the XP-source switch. This is the same defect class as §C1 of `docs/review/harvest-path-review.md`, now with the concrete third-party consumer identified.

**F2 — MEDIUM — Hodgepodge `ServerThreadLongHashMap` gives founder/worker threads a stale or empty chunk map.**
`hp/com/mitchej123/hodgepodge/util/ServerThreadLongHashMap.java:190-206` serves non-owner threads from `getSnapshot()`; `:147-179` creates the snapshot on the server thread with a **250 ms timeout** and falls back to a *stale or empty* map (`LOGGER.warn("Snapshot creation timed out ... serving {} map ...")`). Installed for `ChunkProviderServer` by `hp/com/mitchej123/hodgepodge/core/fml/transformers/mc/SpeedupLongIntHashMapTransformer.java:113-118`. Combined with Hodgepodge's `provideChunk` `@Overwrite` (`hp/.../mixins/early/minecraft/fastload/MixinChunkProviderServer_EntityGuard.java:48-69`: `defaultEmptyChunk` for a missing chunk while loads are blocked), an empty/stale snapshot makes **`world.blockExists` return false / `world.getBlock` return air for chunks that actually exist**, and EZMiner's `Manager` comment (`EZM/core/Manager.java:100-112`) documents that founder threads do exactly this (`world.blockExists` → `chunkExists` → `containsItem`). Ten founder classes read the world this way, e.g. `EZM/core/founder/BasePositionFounder.java:454-455`, `EZM/core/founder/ChainPositionFounder.java:304-305`, `EZM/core/founder/LogFounder.java:71-72`, `EZM/core/founder/OreFounder.java:27-28`. EZMiner's mitigation is **only log filtering** (`EZM/EZMiner.java:74-95`, filter on logger `ServerThreadLongHashMap` for threads named `EZMiner-*`) — it hides the warning but not the stale/empty result (silently missed chain candidates, plus up to 250 ms stalls per first read).
*Minimal fix:* move candidate admission/validation into the server-tick window (as `EZM/chain/planning/ChainPreCalcEngine.java` already does), or re-validate candidates on the server thread before enqueueing; do not treat the log filter as a correctness fix.

**F3 — MEDIUM — CoFH water bridge misses the hole when the cell below the notified water is a non-air replaceable block.**
`EZM/compat/CoFHWaterBridge.java:47-49` and `:87-88` fill only when `world.getBlock(...) == Blocks.air` (identity). Vanilla flows into *any* replaceable cell: `VAN/net/minecraft/block/BlockDynamicLiquid.java:337-341` (`func_149809_q`) + `:307-311` (`func_149807_p`: material != water, != lava, `!blocksMovement`), and `VAN/.../BlockDynamicLiquid.java:172-189` (`func_149813_h`) additionally drops the replaced block. Result: a water source above tall grass / a torch / vines that loses its support is not filled by the bridge and stays visually floating (the notified plant is handled separately only for `BlockBush` — `EZM/compat/BushSupportBridge.java:38-47`).
*Minimal fix:* replace the `== Blocks.air` test with the vanilla replaceability test (material != water/lava && !blocksMovement) on both fill sites; the drop of the replaced block can be skipped because `BushSupportBridge` already handles `BlockBush`.

**F4 — LOW — the bridge's `instanceof BlockDynamicLiquid` branch does not cover the CoFH class that actually replaces `Blocks.water`, nor Forge-fluid water.**
`EZM/compat/CoFHWaterBridge.java:57` (`neighbour instanceof BlockDynamicLiquid`). Real hierarchy: `cofh/asmhooks/block/BlockTickingWater.java:9` (`extends BlockDynamicLiquid`, id 8) **and** `cofh/asmhooks/block/BlockWater.java:9` (`extends BlockStaticLiquid`, id 9); both are installed by `cofh/asm/ASMCore.java:566-575`. `Blocks.water` — the common case (a water *source* above the mined block) — is therefore **not** a `BlockDynamicLiquid`, so the reschedule branch never runs for it (it happens to be unnecessary: `VAN/net/minecraft/block/BlockStaticLiquid.java:27-35` already calls `setNotStationary`, which converts the source to id-1 flowing water and schedules it). Same blind spot for Forge-fluid water: `eio/crazypants/enderio/fluid/BlockFluidEio.java:27` (`extends BlockFluidClassic`), and EZMiner would place **vanilla** `Blocks.flowing_water` (`CoFHWaterBridge.java:49,89`) next to such a fluid whenever its material is `Material.water`.
*Minimal fix:* either drop the branch and document why it is unnecessary, or key it on `neighbour.getMaterial() == Material.water` and schedule `neighbour` (a bare `Block.updateTick` is a no-op for non-liquid blocks, so the wider guard is safe).

**F5 — LOW (documentation / class-hierarchy drift, first-class for this audit) — two compat premises are inverted relative to the real sources.**
(a) `EZM/compat/CoFHWaterBridge.java:13-19` and `AGENTS.md` state that CoFH's water replacement makes `onNeighborBlockChange` a no-op "for water"; in the real hierarchy only the *flowing* replacement inherits the water no-op (`BlockTickingWater extends BlockDynamicLiquid`, whose `onNeighborBlockChange` is inherited from `VAN/.../BlockLiquid.java:538-541` → `func_149805_n`, alive only for lava at `:543-547`), while `Blocks.water` → `BlockWater extends BlockStaticLiquid` whose own `onNeighborBlockChange` **does** react (`VAN/.../BlockStaticLiquid.java:27-35`).
(b) `EZM/compat/NaturaSaguaroCompat.java:22-33` claims `SaguaroBlock` integrity "relies entirely on `onNeighborBlockChange → canBlockStay` self-destruction"; the real method is declared `onNeighborBlockChange(World, int, int, int, int l)` at `nat/mods/natura/blocks/trees/SaguaroBlock.java:213` — an `int` 5th parameter where vanilla requires `Block` (`VAN/net/minecraft/block/Block.java:745`) and it carries **no** `@Override` — so it never runs in-game. EZMiner's cascade is thus not a redundant safety net but the only working mechanism (verdict for the compat itself: OK, see §3.4).
*Minimal fix:* correct both comments and AGENTS.md so future readers do not "simplify away" the cascade or the water fill.

**F6 — LOW — Galacticraft `BlockBasicMoon.breakBlock` side effects are skipped by the EBS path.**
`gc/.../core/blocks/BlockBasicMoon.java:344-376` (footprint cleanup + `TickHandlerServer.footprintBlockChanges` bookkeeping, `meta == 5`) only runs through `Block.breakBlock`. `EZM/chain/execution/ChunkCachedHarvester.java:188-207` calls `onBlockHarvested`/`onBlockDestroyedByPlayer` and writes the EBS directly, and `hasTileEntity(meta)` is true only for meta 15 (`BlockBasicMoon.java:280-283`), so meta 5 takes the fast path and leaves stale footprint entries in `TickHandlerServer.serverFootprintMap`.
*Minimal fix:* extend the "must use the vanilla path" set (`ChunkCachedHarvester.java:133`, currently `hasTileEntity(meta) || DeterminingIdentical.isGTTileEntityCarrier(block)`) with a small compat predicate for `BlockBasicMoon` meta 5.

**F7 — LOW — EFR sweet-berry bush: EZMiner's blind `onBlockActivated` delegate can consume bone meal instead of picking.**
`efr/ganymedes01/etfuturum/blocks/BlockBerryBush.java:107-109` harvests only when `i > 1` *and* (i != 2 || the player is not holding bone meal); at meta 2 with bone meal in hand EFR grows the bush instead. `EZM/compat/EtFuturumCropCompat.java:73-75,84-95` reports meta >= 2 as mature and then delegates to `block.onBlockActivated(...)` unconditionally. Maturity (`meta >= 2`) **matches** the real harvest rule and is correct; the bone-meal nuance is not modelled.
*Minimal fix:* in `EtFuturumCropCompat.harvest`, require meta >= 3, or skip the delegate when the player holds bone meal at meta 2.

**F8 — INFORMATIONAL (no EZMiner fix) — Hodgepodge's `updateTick` chunk guards can permanently suppress a notified neighbour's self-destruct at region borders.**
`hp/.../mixins/early/minecraft/chunkloading/blocks/` guards `updateTick` at HEAD with `cancellable` for `BlockCocoa`, `BlockCrops`, `BlockDynamicLiquid` (which *reschedules* ×5, `MixinBlockDynamicLiquid.java:22-29`), `BlockFarmland`, `BlockFluidClassic`, `BlockFluidFinite`, `BlockMushroom`, `BlockSapling`, `BlockStaticLiquid`, `BlockStem`, `BlockTorch`, and modifies `BlockVine`. EZMiner's notify path (`EZM/chain/execution/ChunkBlockWriteHelper.java:228-294`) triggers the neighbour's `onNeighborBlockChange`; the follow-up scheduled `updateTick` may be cancelled when the surrounding chunks are not loaded. EZMiner compensates only for the `BlockBush` family (`EZM/compat/BushSupportBridge.java`). This is a global Hodgepodge/vanilla behaviour, identical for a player breaking the block by hand, so it is not EZMiner-induced breakage — recorded so it is not re-litigated.
